## When to Use This Skill

Use this skill when an engineer wants to act on an active incident — not just understand it:

- "Fix the checkout service — it's returning 500s"
- "Roll back the payment-api deploy"
- "The alert fired — remediate it"
- "Scale up the order processor, it's saturated"
- "Take action on this incident"
- "Execute a rollback on service X"
- "The database connection pool is exhausted — fix it"
- "Circuit-break the upstream dependency causing cascading failures"
- "Create a ticket for this incident"
- "What should I do to fix this? And do it."

Do NOT use for:
- Pure investigation with no intent to act ("why is it broken?" → use the RCA skill)
- Log retrieval or analytics ("show me errors from the last hour")
- Questions with no active incident or degradation

---

## Mandatory First Step

**If `search_kis` is in your tool list, your FIRST tool call in Phase 1 MUST be
`search_kis`. Do not call `get_logs`, `execute_esql`, or any other tool before it.**

**Tool identity:** Your tool list may show longer registry IDs. These are the same tools:
- Registry ID containing `platform.streams` and ending in `search_kis` → `search_kis`
- Registry ID containing `platform.workflows` and ending in `get_connectors` → `get_connectors`

**If `search_kis` errors** (timeout, permission, internal error): retry **once**.
If it still fails, tell the engineer and **proceed to Phase 1 Track B** — do not block.

## Phase 1 — Diagnose

Reuse the RCA methodology to establish a confirmed root cause before proposing any action.
**Stop at confidence < 70%** — ask the engineer for more context and do not proceed to Phase 2.

### Step 1-0: Extract Context

Before calling any tool, read the engineer's message and note:
- **Symptom**: what is wrong (errors, latency, crashes, saturation, data loss)
- **Suspect**: which service, stream, host, or component
- **Timeframe**: when it started ("since 3pm", "after the deploy", "this morning")
- **Scope**: one service or multiple? User-facing or internal?

Do not invent details not present in the message. Use them to fill in tool parameters precisely.

### Step 1-1: Identify Target Stream and Time Window

**Stream:** Use the service or stream name from Step 1-0 as `stream_names`. If no specific
stream was named, call `search_kis` with no `stream_names` to discover streams with KIs,
present the list, and ask the engineer to confirm before continuing.

**Time window:** Pin a single investigation window.
- "since 3pm" → start = today at 15:00, end = now
- "last 2 hours" → start = now-2h, end = now
- "this morning" → start = today at 00:00, end = now
- No time given → default: start = now-1h, end = now

Use this window consistently in all subsequent queries.

### Step 1-2: Load All Knowledge Indicators

Always start with a targeted call using the symptom as `search_text`:
- `stream_names`: target stream(s) from Step 1-1
- `search_text`: natural-language description of the symptom (e.g. "database connection pool exhaustion", "OOM killed containers")
- `limit`: **50** when not passing `stream_names`; **20** when passing `stream_names`
- No `kind` filter

**If the targeted call returns fewer than 5 KIs**, make a second broader call with no `search_text`:
- Same `stream_names` and `limit`
- Merge results from both calls (deduplicate by ID) before proceeding

### Step 1-3: Form Hypotheses

Read **all** returned KIs and form explicit, testable hypotheses BEFORE executing any queries.

> **Result ordering:** feature KIs appear before query KIs. Query KIs — often the highest-trust
> signals — appear at the **end** of the list. Read through to the end before forming any hypothesis.

Each hypothesis has four parts:
1. **Claim**: "The [component] is failing because [specific mechanism]"
2. **Supporting KIs**: which KIs point to this, with their weight
3. **Confidence**: Speculative / Medium / High / Critical
4. **Test query**: which ES|QL query would confirm or refute it

**Confidence scoring heuristics:**

| Evidence combination | Confidence |
|---|---|
| Backed query with **high** `severity_score` + corroborating `error_logs` feature with **high** `confidence` | Critical |
| Backed query with **high** `severity_score` alone | High |
| `error_logs` feature with **high** `confidence` alone | High |
| Non-backed query with **high** `severity_score` + supporting `log_patterns` feature | Medium-High |
| `error_logs` feature with **mid-range** `confidence` | Medium |
| `log_patterns` feature without corroboration | Medium |
| `dataset_analysis` anomaly | Medium |
| `log_samples` anomaly | Low |

Write out your hypotheses explicitly before testing any:
> H1 (Critical): Payment service database connection pool is exhausted.
>   Supporting: Query KI "DB connection pool exhaustion" (severity=88, backed=true) + Feature KI "error_logs" (confidence=91).
>   Test: execute query KI's esql.query scoped to investigation window.

### Step 1-4: Test Hypotheses — Highest Confidence First

For each hypothesis, execute its test query. Stop when one is confirmed.

**Execution priority:**
- When a hypothesis cites a Query KI, its `query.esql.query` is the **primary** test: call
  `execute_esql` (with time scoping and LIMIT rules below) **before** any `generate_esql`.
- When a hypothesis is Feature-only, scan every Query KI returned in Step 1-2: if any query
  clearly tests the same mechanism, run that `esql.query` via `execute_esql` first.
- Call `generate_esql` only when no loaded Query KI supplies a suitable ES|QL.

**LIMIT / row cap (required):**
- If `LIMIT` is already present in the query, keep it.
- If no `LIMIT` and the pipeline emits one row per document, append `| LIMIT 20` (or `| LIMIT 10` for very wide fields).
- If the query returns a small aggregated result (`STATS` / `COUNT(*)`), no extra `LIMIT` needed.

**Interpretation:**
- Returns rows → condition is firing. Count and content confirm severity.
- Returns 0 rows → condition is NOT active. Mark refuted and move on immediately.
- Returns an error → try adapting the query (add time filter, fix field name). If still failing, skip.

If ALL hypotheses are refuted, proceed to Track B below.

### Step 1-5: Establish Timeline and Blast Radius

Once a hypothesis is confirmed, run two additional queries:

**Onset** — when did it start?
Prefer adapting the confirmed Query KI pipeline with `MIN(@timestamp)` in a `STATS` clause
and calling `execute_esql` before `generate_esql`. Cross-reference with the Feature KI's
`last_seen` field as a sanity check.

**Blast radius** — what else is affected?
Extend the confirmed pipeline with a grouping `STATS` (e.g. by `service.name` or `host.name`).
If the KI filter scopes to a single service, the failure may be contained; if broad, wider impact.

### Step 1-6: Root Cause Statement

Produce:
- **Root Cause** (or "Most Likely Cause" if not yet confirmed)
- **Confidence score** (0–100%). If < 70%, stop and ask for more context.
- **Evidence table**: Source / Details / Weight
- **Timeline**: when it started, ongoing or resolved
- **Blast radius**: which services/components, how many events

**Stop if confidence < 70%.** State what additional information would raise confidence,
and ask the engineer to provide it. Do not proceed to Phase 2.

### Phase 1 — Track B: Log Funnel (Fallback)

Enter this track if `search_kis` is not in your tool list, **failed after one retry**,
returned no KIs after two attempts, or all KI-derived hypotheses were explicitly refuted.

**Phase B-1 — Initial Peek:**
Call `get_logs` with no `groupBy`. Scope with `kqlFilter` if the engineer named a service.
Read: `totalCount` (noise indicator), `histogram` (spike location), `samples` (real errors?),
`categories` (< 20 = focused enough), `topValues` (use exact values in subsequent KQL filters).

Decision: < 20 categories → Answer. Spike visible → Phase B-2. ≥ 20 noisy → Phase B-2.

**Phase B-2 — Log Rate Analysis:**
Call `run_log_rate_analysis`.
- Spike visible: baseline = before spike, deviation = during spike.
- User named a time: use that as the boundary.
- No spike/context: baseline = now-2h to now-1h, deviation = now-1h to now.

If it returns nothing (steady-state), go to Phase B-3.

**Phase B-3 — Reduce Noise:**
Call `get_logs` repeatedly. Two strategies:
- **Exclude noise**: accumulate NOT clauses (never drop previous ones). `NOT message: "GET /health"`
- **Zoom into signal**: once you identify the signal, switch to positive filter. `service.name: "checkout" AND log.level: "error"`
Use exact values from `topValues`. Call `get_logs` at least 3 times before answering.

Produce the same root cause statement, evidence, timeline, and blast radius as Step 1-6.
Apply the same 70% confidence threshold before proceeding to Phase 2.

## Phase 2 — Discover & Propose

Only enter Phase 2 when confidence ≥ 70%.

### Step 2-1: Classify Action Type

Map the confirmed root cause to one of these action types:

| Action Type | When to use |
|---|---|
| `ROLLBACK` | Error spike traceable to a recent deployment (within the last 2 hours) |
| `SCALE` | CPU, memory, queue, or connection pool saturation |
| `CIRCUIT_BREAK` | Upstream dependency failure causing cascading errors downstream |
| `CONFIG_CHANGE` | Misconfiguration revealed in KI or ES|QL evidence |
| `TICKET_ONLY` | No safe automated action available; incident requires human judgment |

When multiple action types apply, prefer the more reversible one:
**ROLLBACK > SCALE > CIRCUIT_BREAK > CONFIG_CHANGE > TICKET_ONLY**

### Step 2-2: Check Available Connectors

Call `get_connectors` to discover what is already configured in this environment.
Filter by the `actionTypeId` that matches the action type and detected environment:

| Action type + environment | `actionTypeId` to query |
|---|---|
| ROLLBACK / SCALE / CIRCUIT_BREAK on K8s, ArgoCD, GCP, AWS | `.webhook` |
| ROLLBACK / SCALE via GitHub Actions pipeline | `.github` |
| Incident notification | `.slack` |
| Alert management | `.pagerduty` |
| Ticket creation | `.jira` or `.servicenow` |

Call `get_connectors` once per action type needed. Read each result's `name` and `stepTypes`
to understand what the connector does.

**If `get_connectors` returns connectors:** one or more execution paths are available.
Note the connector `id` — you will use it in Phase 3.

**If `get_connectors` returns empty for the needed `actionTypeId`:** no connector is
configured for this action. Mark the action `MANUAL` and go to Fallback for that action.

Also check for incident management connectors (`.slack`, `.pagerduty`, `.jira`) regardless
of the primary action type — always use them if available to notify and create a ticket.

### Step 2-3: Match Action to Connector or Workflow

For each required action:
1. If `get_connectors` returned a connector for this action type → plan to use it.
   Note: the `connector-step` execution tool is coming soon. For now, use your
   workflow-authoring capability to create a one-step workflow using the connector ID,
   then run it.
2. If no connector matched → check available workflows via workflow-authoring (`list_workflows`).
   A pre-built workflow may already exist for this action.
3. If neither connector nor workflow is available → mark `MANUAL`.

Extract ALL required parameters from investigation evidence. Never invent a value:
- `service_name` ← alert context, ES|QL result, or stream name
- `namespace` ← `kubernetes.namespace` field or alert metadata
- `target_version` ← KI deployment event or previous image tag found in logs
- `environment` ← stream name or log fields
- `connector_id` ← from `get_connectors` result

If a required parameter cannot be sourced from the evidence, name it explicitly and ask
the engineer to supply it. Do not proceed until all parameters are known.

### Step 2-4: Present Structured Plan

Present the full remediation plan before doing anything:

**Root Cause:** [one sentence, confidence %]
**Blast Radius:** [which services / how many events]
**Timeline:** [when it started / ongoing or resolved]

**Proposed Actions** (in order — most reversible first):

For each action:
- **Action N**: [action type] — [what will happen in plain English]
  - Connector: [connector name + actionTypeId] (or Workflow: [name]) (or MANUAL if neither available)
  - Parameters: [each parameter and its source from evidence]
  - Expected outcome: [what should improve and how you will verify it]
  - Risk level: Low / Medium / High — [one sentence rationale]
  - Fallback if declined: [what to do instead]

**If ALL proposed actions are MANUAL** (no workflows matched any action type):
Do NOT ask "Shall I proceed?" — skip Phase 3 entirely and go directly to the
**Fallback — Connector Gap** section immediately.

**If at least one action has a matching workflow:**
Ask the engineer: "Shall I proceed with Action 1 first? Please confirm or decline each action."

## Phase 3 — Confirm & Execute

**One action at a time. Never execute in parallel. Never skip confirmation.**

### Step 3-1: Confirm Before Every Action

Before running any workflow, call `request_confirmation` with:
- `prompt_id`: a short stable string identifying this specific action,
  e.g. `"rollback-payment-api"` or `"scale-order-processor"`.
  **Use the same value if the tool is called again for the same action.**
- `title`: short action label shown in the UI,
  e.g. `"Roll back payment-api to v2.4.0"`
- `message`: the full pre-action explanation the engineer reads before deciding:
  - Workflow tool name and what it does
  - Exact parameters with the evidence source for each value
  - Expected outcome (specific and measurable)
  - Risk level and what happens on failure
  - What you will do if the engineer declines

Do NOT run the workflow until `request_confirmation` returns `"accepted"`.

On **`"accepted"`**: proceed to Step 3-2.
On **`"rejected"`**: STOP immediately. Do not proceed to the next action.
  - Summarise what has run vs what has not.
  - State current incident status based on last ES|QL result.
  - Ask what the engineer would like to do instead.

### Step 3-2: Execute and Verify

1. Execute the action using the connector or workflow identified in Phase 2:
   - **Connector path**: use your workflow-authoring capability to create a one-step workflow
     with the connector `id` from `get_connectors`, then run it immediately.
   - **Workflow path**: if a pre-existing workflow matches, run it directly via workflow-authoring.
2. Report the result verbatim (success response or error message).
3. Wait 60–90 seconds for the action to take effect (state this explicitly).
4. Re-run the diagnostic ES|QL from Phase 1 against the same investigation window extended to now.
5. Compare to the pre-action baseline:
   - Error count before: N. Error count after: M. Delta: N-M (improvement / no change / regression).
   - If the signal improved: state by how much and whether the incident is resolved.
   - If the signal is unchanged after 5 minutes: report this honestly — do not retry automatically.
     Ask the engineer how to proceed.
   - If the signal worsened: report immediately and stop. Propose rollback of the action if applicable.

### Step 3-3: On Workflow Error

If the workflow returns an error:
- Report the error verbatim.
- Do NOT retry automatically.
- Ask the engineer: "The workflow returned an error. Shall I retry, try a different action, or stop?"

### Step 3-4: Completion

After all approved actions are executed and verified:
- State whether the incident is resolved, partially resolved, or unresolved.
- If resolved: summarise what was done, what the evidence shows, and recommend a post-incident review.
- If unresolved: state what was tried, what the current signal shows, and what the next options are.
- If the incident resolved before all proposed actions completed: stop and say so explicitly.
  Do not execute remaining actions unnecessarily.

## Fallback — Connector Gap

When no available workflow matches the required action type, do not produce generic shell commands.
Instead: infer the environment from Phase 1 evidence, identify exactly which connector is
missing, give the engineer a specific setup guide, and provide immediate manual steps
to stop the bleeding right now.

### Step F-1: Infer Environment from Evidence

Read log fields and KI metadata from Phase 1. Only assert what the evidence actually shows.

**Kubernetes signals** (any one is sufficient):
- `kubernetes.namespace` field present in log documents
- `orchestrator.cluster.name` or `orchestrator.type: "kubernetes"` present
- Stream name contains `k8s`, `kube`, or a known namespace pattern

**GitOps layer** (refines Kubernetes — check for these labels):
- ArgoCD: `argocd.io/app-name` or `app.kubernetes.io/instance` label
- Helm: `helm.sh/chart` or `app.kubernetes.io/managed-by: "Helm"` label
- Flux: `kustomize.toolkit.fluxcd.io/name` label

**Cloud provider:**
- `cloud.provider: "aws"` or `aws.*` log fields → AWS (ECS, Lambda, or EC2)
- `cloud.provider: "gcp"` or `gcp.*` log fields → GCP (Cloud Run, GKE, or GCE)
- `cloud.provider: "azure"` or `azure.*` log fields → Azure (AKS, Container Apps)

**Data tier:**
- `db.system: "postgresql"` or `db.system: "mysql"` → RDBMS
- `messaging.system: "kafka"` → Kafka
- `db.system: "redis"` → Redis

**CI/CD:**
- KI deployment event referencing a commit SHA, PR number, or branch → GitHub or GitLab
- KI referencing a Jenkins build number → Jenkins

### Step F-2: Map Action Type to Required Connector

#### ROLLBACK

| Environment detected | Connector needed | Operation |
|---|---|---|
| ArgoCD-managed K8s | **ArgoCD** | Sync application to a pinned revision (last healthy commit) |
| Helm-managed K8s | **Helm via CI/CD** | `helm rollback {release} {revision}` triggered through GitHub/GitLab pipeline |
| Plain K8s (no GitOps) | **Kubernetes API** | Patch deployment to previous image tag |
| GitHub-sourced deploy | **GitHub Actions** | Dispatch rollback workflow via `workflow_dispatch` |
| GitLab CI deploy | **GitLab** | Trigger rollback pipeline on pinned ref |

#### SCALE

| Environment detected | Connector needed | Operation |
|---|---|---|
| K8s deployment | **Kubernetes API** | Patch deployment scale subresource |
| GKE / GCP | **GCP** | Update node pool size or Cloud Run instance limits |
| ECS / AWS | **AWS** | UpdateService — set `desiredCount` |
| Cloud Run | **GCP** | Patch service `maxInstances` |
| Azure Container Apps | **Azure** | Patch container app replica count |

#### CIRCUIT_BREAK

| Environment detected | Connector needed | Operation |
|---|---|---|
| Istio service mesh | **Kubernetes API** | Patch VirtualService — inject fault abort rule at 100% |
| Nginx ingress | **Kubernetes API** | Patch Ingress or ConfigMap — set upstream weight to 0 |
| Cloudflare (edge) | **Cloudflare** | Toggle firewall rule or rate-limit rule for the affected origin |
| HAProxy / Nginx (bare metal) | **Ansible** | Run playbook to reload config with upstream disabled |

#### CONFIG_CHANGE

| Environment detected | Connector needed | Operation |
|---|---|---|
| K8s ConfigMap / Secret | **Kubernetes API** | Patch ConfigMap or Secret with corrected value |
| Helm values | **Helm via CI/CD** | `helm upgrade --set {key}={value}` through pipeline |
| GitOps (ArgoCD or Flux) | **GitHub / GitLab** | Open PR with corrected value — engineer merges to deploy |
| Host configuration | **Ansible** | Run targeted playbook via AWX/AAP |
| Terraform-managed infra | **GitHub Actions / GitLab CI** | Trigger `terraform apply -target={resource}` |

#### DATA TIER

| Symptom | Connector needed | Operation |
|---|---|---|
| PostgreSQL connection pool exhausted | **PostgreSQL** (via HTTP sidecar or Ansible) | Kill idle connections: `pg_terminate_backend` where `state = 'idle'` |
| PostgreSQL slow query spike | **PostgreSQL** | Cancel long-running queries: `pg_cancel_backend` for queries over 30s |
| Redis memory pressure / evictions | **Redis** (via HTTP wrapper or Ansible) | Flush targeted key namespace |
| Kafka consumer group lag | **Kafka** (via Confluent REST or Ansible) | Reset offsets to latest or pause consumer group |

#### NETWORKING & ROUTING

| Symptom | Connector needed | Operation |
|---|---|---|
| Certificate / TLS issue | **Kubernetes API** | Patch Secret with renewed certificate |
| DNS / CDN cache stale | **Cloudflare** | Purge cache for the affected zone or URL pattern |
| Rate limiting flood | **Cloudflare** | Enable under-attack mode or tighten rate-limit threshold |

#### SECRETS & ACCESS

| Symptom | Connector needed | Operation |
|---|---|---|
| Leaked or expired credential | **HashiCorp Vault** | Revoke specific lease or rotate secret at the mount path |
| Service account token expired | **Kubernetes API** | Rotate ServiceAccount token Secret |

#### INCIDENT MANAGEMENT (always propose even without execution connectors)

| Action | Connector needed | Operation |
|---|---|---|
| Notify and track | **Slack** | Post root cause + blast radius + action plan to war room channel |
| Page on-call | **PagerDuty / OpsGenie** | Trigger incident; attach evidence; check on-call schedule |
| Create ticket | **Jira / ServiceNow** | Create incident pre-populated with full evidence table |
| Create issue | **GitHub** | Open GitHub Issue on the affected repo with root cause, blast radius, and resolution steps |
| Look up ownership | **Backstage** | Retrieve service owner, SLO targets, and runbook link |

#### ALERT MANAGEMENT

| Action | Connector needed | Operation |
|---|---|---|
| Suppress alert storm during known incident | **Prometheus / Alertmanager** | POST silence scoped to service label for a bounded window |

### Step F-4: Connector Setup Guides

Present the setup guide for the specific connector(s) identified in Step F-2.

---

**ArgoCD Connector** (Webhook)

- Endpoint: `https://{argocd-server}/api/v1/applications/{app}/sync`
- Method: POST
- Auth: Bearer token — `argocd account generate-token --account {svc-account}`
- Headers: `Content-Type: application/json`, `Authorization: Bearer {token}`
- Body: `{"revision": "{target_revision}", "prune": false, "dryRun": false}`
- Minimum RBAC: `p, role:agent, applications, sync, */*, allow` in ArgoCD RBAC policy

---

**Kubernetes API Connector** (Webhook)

For rollback (patch image tag):
- Endpoint: `https://{kube-apiserver}/apis/apps/v1/namespaces/{ns}/deployments/{name}`
- Method: PATCH, Content-Type: `application/strategic-merge-patch+json`
- Auth: ServiceAccount Bearer token — minimum ClusterRole:
  ```yaml
  rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "patch", "update"]
    resourceNames: ["{deployment-name}"]
  ```

For scale:
- Endpoint: `.../deployments/{name}/scale`
- Body: `{"spec": {"replicas": N}}`

---

**GitHub Actions Connector** (Webhook)

- Endpoint: `https://api.github.com/repos/{owner}/{repo}/actions/workflows/{workflow-id}/dispatches`
- Method: POST
- Auth: `Authorization: Bearer {PAT}` — PAT needs `actions:write` scope on the repo
- Headers: `Accept: application/vnd.github+json`, `Content-Type: application/json`
- Body:
  ```json
  {
    "ref": "main",
    "inputs": {
      "service": "{service_name}",
      "environment": "{environment}",
      "action": "rollback",
      "target_version": "{target_version}"
    }
  }
  ```
- Note: the workflow must have a `workflow_dispatch` trigger accepting these inputs.

---

**AWS Connector** (Webhook — ECS UpdateService)

- Endpoint: `https://ecs.{region}.amazonaws.com/` — sign requests with AWS SigV4
- IAM minimum policy:
  ```json
  {"Action": ["ecs:UpdateService", "ecs:DescribeServices"],
   "Resource": "arn:aws:ecs:{region}:{account}:service/{cluster}/{service}"}
  ```
- For rollback: update `taskDefinition` to `{family}:{previous-revision}`
- For scale: update `desiredCount`

---

**GCP Connector** (Webhook)

Auth: Service account key or Workload Identity.

Cloud Run scaling:
- Endpoint: `https://run.googleapis.com/v1/projects/{project}/locations/{region}/services/{name}`
- Method: PATCH — update `spec.template.spec.containerConcurrency` or autoscaling annotations
- Role needed: `roles/run.admin` scoped to the service

GKE: use the Kubernetes API connector with the GKE API server URL.

---

**Kafka Connector** (Webhook — Confluent REST Proxy or custom sidecar)

For consumer group lag:
- Confluent Cloud: `https://api.confluent.cloud/kafka/v3/clusters/{cluster-id}/consumer-groups/{group-id}`
- Auth: API Key + Secret (Basic auth)
- For offset reset: trigger via Ansible playbook or custom HTTP endpoint accepting `{"action": "reset", "group": "{group_id}", "topic": "{topic}", "to": "latest"}`

---

**PostgreSQL Connector** (via HTTP sidecar or Ansible AWX)

PostgreSQL TCP cannot be called directly from a Webhook. Options:
1. Deploy a lightweight HTTP sidecar accepting `{"action": "kill_idle"}` and executing:
   `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND query_start < NOW() - INTERVAL '30s'`
2. Ansible AWX connector — run a playbook that executes the SQL
- DB user permission needed: `pg_signal_backend` role (avoid SUPERUSER)

---

**Redis Connector** (via HTTP wrapper or Ansible AWX)

Redis TCP cannot be called directly. Options:
1. Custom HTTP wrapper accepting `{"action": "flush_namespace", "pattern": "{prefix}:*"}`
2. Ansible AWX playbook

---

**Slack Connector** (built-in Kibana connector)

Stack Management → Connectors → Slack → Incoming Webhook.
Configure the webhook URL from your Slack app settings.
In the workflow: post to `#{incident-channel}` with root cause, blast radius, and action plan.

---

**PagerDuty Connector** (built-in Kibana connector)

Stack Management → Connectors → PagerDuty.
Provide the Integration Key (Events API v2).
Workflow operations: trigger, acknowledge, resolve, or annotate an incident.

---

**Jira / ServiceNow Connector** (built-in Kibana connectors)

Stack Management → Connectors → Jira (or ServiceNow).
Pre-populate tickets with: root cause, confidence %, evidence table, blast radius,
timeline, connector gap report, and Phase 1 ES|QL query links.

**GitHub Connector** (Webhook — Issues API)

Use when the team tracks incidents via GitHub Issues, or when the affected service's
repo is on GitHub and the engineer prefers issues over a separate ticketing system.

- Endpoint: `https://api.github.com/repos/{owner}/{repo}/issues`
- Method: POST
- Auth: `Authorization: Bearer {PAT}` — PAT needs `issues:write` scope on the repo
- Headers: `Accept: application/vnd.github+json`, `Content-Type: application/json`
- Body template:
  ```json
  {
    "title": "[Incident] {service_name} — {root_cause_summary}",
    "body": "## Root Cause\n{root_cause}\n\n## Evidence\n{evidence_table}\n\n## Blast Radius\n{blast_radius}\n\n## Timeline\n{timeline}\n\n## Resolution Steps\n{manual_steps}",
    "labels": ["incident", "on-call"],
    "assignees": ["{on_call_github_username}"]
  }
  ```
- Populate `body` fields from Phase 1 evidence. Include ES|QL query links and KI IDs.
- Tip: use GitHub connector for repos that already have incident label workflows or
  auto-routing via CODEOWNERS — the issue lands directly in the right team's backlog.

### Step F-5: Immediate Manual Steps

While connectors are being set up, provide the fastest safe path to stop the incident NOW.

  AND state = 'idle'

## Critical Rules

1. **NEVER run a workflow without explicit prior engineer confirmation via `request_confirmation`.**
   Confirmation means the engineer has clearly said "yes", "proceed", "do it", or equivalent
   for that specific action. Silence is not consent.

2. **NEVER invent parameter values.** Every parameter passed to a workflow must trace to a
   specific piece of investigation evidence: a KI field, an ES|QL result row, an alert field, or
   an explicit engineer-supplied value. If a value cannot be sourced, ask.

3. **ALWAYS verify with ES|QL after each action before moving to the next.** Never chain two
   workflow calls without an intermediate verification step showing the effect of the first.

4. **ALWAYS express confidence level and what drives uncertainty.** If confidence is below 70%,
   do not enter Phase 2. If evidence is incomplete, say so explicitly.

5. **Actions are sequential — never propose or execute in parallel.** Each action must be
   confirmed, executed, and verified before the next is proposed.

6. **If the incident resolves before all proposed actions complete: stop and say so.** Do not
   execute remaining actions for completeness. Unnecessary changes are risk.

7. **Prefer reversible actions first.** Rollback before config change; scale before disable.
   If multiple actions of equal reversibility apply, prefer the one with narrower blast radius.

8. **On workflow error: report verbatim, do not retry automatically.** Ask the engineer to decide.

9. **Do not fabricate.** Never invent KI scores, ES|QL results, tool outputs, or service names.

## OTel Exception Events

OpenTelemetry exception events have `error.exception.message` / `error.exception.type` but NO
`log.level` or `message`. In `get_logs` results they appear as categories with `type: "exception"`.
Filter explicitly: `error.exception.message: *`. Invisible to `log.level`-based KQL filters.

---

## Tips

- **KQL for `kqlFilter`:** Follow the KQL (Kibana Query Language) section in the host agent's
  system instructions when building filters for `get_logs` and related tools.
- **ES|QL + context:** `FROM` without `STATS` / tight aggregation can return huge row sets; add
  `| LIMIT 20` (or lower) before executing unless the query already has `LIMIT` or returns a small aggregate.
- `log.level` is often unreliable (mixed casing, missing on OTel events). Prefer filtering by message content.
- Use `get_index_info(operation="get-field-values", fields=["log.level"], ...)` to discover actual keyword values before filtering.
- To inspect a specific document: `get_logs(kqlFilter="_id: \"<doc_id>\"", fields=["message","error.stack_trace"])`.
- To see surrounding context: `get_logs` with a ±30s window around the event timestamp, scoped to the same entity, limit=50.

## Example Investigation

**Engineer:** "The payment service has been throwing database errors since 2pm. Fix it."

**Phase 1 — Diagnose:**

Step 1-0: Symptom = database errors. Suspect = payment service. Timeframe = since 14:00.

Step 1-1: stream = "payment", window = 14:00 → now.

Step 1-2 (targeted): search_kis(stream_names=["payment"], search_text="database errors", limit=20)
→ Returns 4 KIs:
  - Feature KI F1: type="error_logs", confidence=93, description="FATAL: connection pool exhausted — all 100 slots occupied", filter={"field":"service.name","eq":"payment"}, status="active"
  - Feature KI F2: type="log_patterns", confidence=61, description="Slow query warnings from PostgreSQL", status="stale"
  - Query KI Q1: "DB connection pool exhaustion" (severity=88, backed=true, esql="FROM payment | WHERE error.message LIKE \"*too many connections*\" | STATS count=COUNT(*)")

Step 1-3 — Hypotheses:
> H1 (Critical): Payment service has exhausted its database connection pool.
>   Supporting: Q1 (backed, severity=88) + F1 (error_logs, confidence=93).
>   Test: execute Q1's esql scoped to 14:00–now.

Step 1-4 — Test H1:
execute_esql(Q1 query, time_range={from:"14:00", to:"now"})
→ count=1,847 — firing.
→ H1 = Confirmed.

Step 1-5: MIN(@timestamp) ≈ 13:57. Blast radius: payment service only (F1 filter).

Step 1-6 — Root Cause Statement:
Root Cause (Confirmed, 92%): The payment service exhausted its PostgreSQL connection pool
at approximately 13:57. 1,847 "too many connections" events are active. Only the payment service
is affected. Confidence: 92% (two corroborating KIs, backed rule, live query confirmed).

**Phase 2 — Discover & Propose:**

Action type: SCALE (connection pool saturation — not a recent deploy, no upstream failure).

Available workflows (discovered via workflow-authoring): `scale_deployment`
(increases replica count for a Kubernetes deployment).

Parameters:
- `service_name`: "payment" (from stream name and F1 filter)
- `namespace`: "prod" (from log field `kubernetes.namespace` = "prod" in ES|QL result)
- `replicas`: 6 (current 3 × 2, to reduce per-replica connection load)

Proposed Plan:
> Root Cause: PostgreSQL connection pool exhausted on payment service (92% confidence).
> Blast Radius: payment service only, 1,847 active errors.
> Timeline: onset 13:57, ongoing.
>
> Action 1: SCALE — scale_deployment(service_name="payment", namespace="prod", replicas=6)
>   Expected outcome: per-replica connection pressure halves; error rate should drop within 60–90s.
>   Risk: Low — scaling up is fully reversible.
>   Fallback if declined: kubectl scale deployment/payment --replicas=6 -n prod
>
> Shall I proceed with Action 1?

**Phase 3 — Confirm & Execute:**

Engineer: "Yes, proceed."

Step 3-1: calls request_confirmation → engineer clicks Proceed.
Running workflow: scale_deployment(service_name="payment", namespace="prod", replicas=6)
→ Result: "Deployment payment scaled to 6 replicas. Rollout in progress."

Waiting 60–90 seconds for the rollout to complete...

Verification — re-running Q1 ES|QL scoped to 14:00–now:
→ count=94 — down from 1,847. Error rate dropped by 95%.

**Incident is resolved.** The payment service connection pool is no longer saturated.
Recommend post-incident review: investigate what triggered the connection surge at 13:57,
and consider adding a connection pool size limit as a KI-backed alert.
